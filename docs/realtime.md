# 100 Hz 硬件循环：预算、诊断与验收

## 目标与边界

舵机 I/O 目标周期为 **10 ms（100 Hz）**，策略推理周期为 **20 ms（50 Hz）**。两者不能混为一谈，也不能把配置中的 `hardware_loop_hz=100` 当作实际达到 100 Hz 的证据。Web 的 `feedback_hz` 是控制器收到反馈的频率，`hardware_timing.measured_hz` 则来自硬件循环的真实开始时间。

当前 Python/Linux 实现不是硬实时保证。只有在目标 Linux 设备、实际串口适配器、15 个舵机、IMU 和正常推理/Web 负载下完成验收，才能判断当前部署是否持续满足要求。维护操作包含 EEPROM 写入间隔与标零等待，不承诺维护期间仍达到 100 Hz。

## 周期执行

每个周期依次处理维护请求、读取 IMU、消费最新命令、检查使能条件、写入舵机目标、采集舵机反馈并发布状态。

串口回复采用增量解析。在 15 个不同 ID 的完整、校验正确、状态正常且长度匹配的回复全部收齐时立即返回。缺失 ID、重复帧、错误状态和损坏帧不能使读取提前完成；缺失反馈时等待 6 ms 截止时间，并返回已经收到的有效反馈。

串口暂不可读时使用文件描述符可读等待。发送后的 `flush()` 用于等待发送完成；半双工收发约束不能通过直接省略发送等待来绕过。

循环按 10 ms 绝对截止时间调度。超预算后跳过已错过的调度周期，不追赶式突发发送旧目标。命令新鲜度、显式 ARM、命令/IMU 超时卸力和维护操作间隔均属于执行约束。

## 耗时数据

`GET /api/status` 通过 `hardware_timing` 提供循环时序。采样有界，最多保存最近 500 个周期；硬件线程只记录样本，统计排序在 HTTP 线程执行，且不占用控制器状态锁。

| 字段 | 含义 |
| --- | --- |
| `target_hz` / `budget_ms` | 配置目标 100 Hz / 10 ms，不是实测值 |
| `measured_hz` | 窗口内 `(周期数 - 1) / 首尾开始时间差`；无足够样本时为 null |
| `stale` / `sample_age_ms` | 样本是否过期及其年龄；停止后的历史频率不能当作当前频率 |
| `window_cycles` / `window_span_s` | 窗口大小和时间跨度；低频时 500 周期可能超过 5 秒 |
| `cycles_total` / `missed_deadlines_total` | 启动以来完成的周期和错过的调度周期 |
| `period_ms` | 实际周期的 mean / p99 / max |
| `wakeup_lateness_ms` | 线程相对计划开始时间的唤醒延迟 |
| `work_ms` | 从周期开始到反馈发布完成的分段耗时之和，包含回调，不包含统计入队和周期等待 |
| `stages_ms.services` | 校准/维护队列处理及循环起始开销 |
| `stages_ms.imu` | IMU 读取耗时 |
| `stages_ms.command_write` | 命令校验、扭矩/增益变更和目标写入耗时 |
| `stages_ms.servo_read` | 舵机同步读取：发送、等待及帧解析 |
| `stages_ms.feedback_publish` | 反馈组装和控制器回调，包括回调等待锁的时间 |
| `maintenance_cycles` | 窗口中处于标零/维护模式的周期数 |

`hardware_work_us` 不包含反馈回调的执行时间，不能单独用于判断完整周期是否有足够余量。`hardware_timing.work_ms` 包含反馈回调成本，可用于评估完整工作阶段。

## 上机验收

先按 `validation.md` 做安全准备。本工具**只读取状态**，不会使能舵机、发送运动或修改维护参数。先让服务运行至少 5 秒，再执行：

```bash
python tools/check_control_rate.py --url http://127.0.0.1:9527 --duration 60
```

默认验收条件：窗口实测频率至少 98 Hz、窗口至少 3 秒、验收期间漏周期计数不增加、样本新鲜、15 个舵机在线、IMU 有效且不处于维护模式。未满足时退出码为 1，并打印具体原因与各阶段 p99。98 Hz 是可调整的工程验收阈值（`--min-hz`），不改变 100 Hz 的调度目标；通过此检查也不证明每个周期都不超过 10 ms。

建议分别记录：

1. `shadow` 空载运行。
2. 按安全流程悬空固定后，显式进入 `hold`、`policy`，观察实际目标写入及推理负载。
3. 打开 Web 工作台并进行正常交互，确认没有新增漏周期。
4. 延长到 10 分钟以上测试，并检查 `period_ms.max`、工作耗时与唤醒延迟的 p99/max，而不只看平均频率。
5. 独立验证断网、缺失舵机、IMU 失效、命令超时与维护退出的安全行为；这些故障场景不强求完整反馈 100 Hz。

## 频率不足的诊断

- **`servo_read` 高**：先查看缺失 ID，再检查总线接线、串口适配器和回复时序；收不齐的周期仍会等满超时。不要直接缩短超时隐藏丢帧。
- **`command_write` 高**：检查串口发送/排空和模式切换写入；遵守半双工约束，不直接去掉 `flush()`。
- **`imu` 高**：检查 I2C 读取及设备错误。
- **`feedback_publish` 高**：重点定位控制器回调及共享锁竞争，再决定是否需要快照/线程隔离。安全相关反馈在硬件循环内同步发布。
- **工作耗时低但唤醒延迟高**：检查系统负载和调度；必要时在目标环境评估线程/进程隔离或实时内核，而不是默认用 root 实时优先级运行整个 Web 服务。
